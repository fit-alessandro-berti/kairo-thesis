# Kairo and PM4Py concept drift assessment

The [final report](FINAL_REPORT.md) summarizes what the benchmark shows about Kairo's detection quality.

Each dataset has a [results folder](results/) with a `dataset.json` recording source provenance, dimensions, and ground truth. The runs live under `<dataset>/<library>/<method>/<profile>.json`. Each records effective configuration, drift timestamps, confirmation times where available, evidence scores, and evaluation. PM4Py intervals and inferred versions are included where returned. The [manifest](results/manifest.json) records the assessed revisions and dependencies.

The assessment has 1,030 result files. All 616 PM4Py configurations and 376 Kairo configurations completed. In 30 Kairo configurations the input has no resource field, and eight intra-case DBSCAN configurations exceed the 10,000 distinct feature-row limit used for this benchmark. Those files record the reason.

## Selected comparisons

These examples use the primary 2.5% matching tolerance. They illustrate how the input representation, signal profile, and reporting time affect the results.

- Among profiles run on all 23 logs, PM4Py's version clustering had the highest micro F1 at 0.484, with 15 of 37 episodes matched and 10 false alarms. Kairo's highest was 0.323 for previous-window intra-case K-means, with 21 episodes matched and 72 false alarms. These totals sum the per-log counts, including false alarms on the controls.
- Both PM4Py DFG frequency profiles found the change on all three Ceravolo logs with zero false alarms. On the Rheon log with four sudden control-flow changes, the wide trace-variant test also found all four with zero false alarms. Kairo's previous-window intra-case SOM found all four plus one additional alarm. [Ceravolo results](results/cdrift_ceravolo_rio/pm4py/dfg-frequency/), [Rheon trace-variant results](results/rheon_multi_02/pm4py/trace-variant-frequency/permutation-wide.json), [Rheon Kairo intra-case results](results/rheon_multi_02/kairo/intra-som/previous.json).
- On Rheon's sudden reassignment log, all three Kairo recent-window resource profiles found the change without extra alarms. PM4Py's resource MMD and enriched PELT each found it with one additional alarm. On the gradual waiting-time log, Kairo's recent-window inter-case SOM had one match and zero extra alarms. The cleanest PM4Py profile with a match was trained cluster frequency, with one additional alarm. [Reassignment results](results/rheon_single_11/), [waiting-time results](results/rheon_single_15/).
- For Rheon's three region-composition changes, Kairo's inter-case SOM found three with two additional alarms using its previous-window profile and two without extra alarms using its recent-window profile. PM4Py's generic PELT and flow/timing MMD found none. With explicit region shares and amount means for PELT, and categorical region and numeric amount for MMD, both recovered all three with zero false alarms even at 1%. [Rheon inter-case SOM](results/rheon_multi_03/kairo/inter-som/), [PM4Py case-composition diagnostics](diagnostics/case-composition/rheon_multi_03/).
- On the three Padella control-flow logs, Kairo's recent-window intra-case SOM and PM4Py's version clustering each matched all three injections and emitted two additional alarms. Timing changes were harder to isolate. Kairo's previous-window resource SOM and PM4Py's fixed Page–Hinkley conformance each matched two of the three timing injections and emitted nine additional alarms across the three timing logs. [Padella results](results/).

## Method

- The input scope is a purposive sample of 23 complete logs with 1,086,668 events and 37 annotated temporal episodes. It includes eight Padella logs from five real base processes, nine Rheon logs from the thesis, and six archived logs from the Bose, Ceravolo, and Ostovar families. The sample includes sudden, gradual, and recurring changes in control flow, timing, workload, assignments, and case composition. Natural variation in the two Padella controls can still produce alarms because the labels describe injected changes. [Thesis evaluation](../../thesis/chapters/evaluation.tex), [historical benchmark](https://github.com/cpitsch/cdrift-evaluation), [Padella archive](https://zenodo.org/records/21005862).
- The Bose archive reuses literal case identifiers, so input loading preserves each of the 6,000 physical XES traces as a distinct case. The three Ceravolo files store numeric identifiers in lexicographic order. The core protocol uses the timestamp of case 500, the first case in the second chronological half, and stores the archived XML ordinal and its timestamp for traceability. [Ceravolo source dataset](https://doi.org/10.21227/2kxd-m509).
- Each PM4Py variant runs through the branch's public dispatcher. Its native alarms supply the drift estimates. PM4Py variants differ in which attributes they model and in whether they analyze the complete log or report after a confirmation window. The supervised similarity prototype learns from 24 independently generated control-flow logs using the branch's patch classifier. Its results measure that fitted prototype. The public CV4CDD-4D weights are a different configuration.
- The conformance-profile runs use PM4Py's exact memory-efficient Dijkstra option for alignment-automaton precision. It improved runtime in the noisy Ceravolo pilot. An exact solver can choose a different optimal path when costs tie, so the precision values can differ from a run with state-equation A*. [Solver pilot](diagnostics/conformance-alignment.json).
- On Ostovar parallel-to-sequence, the initially mined Petri net made exact alignment impractical. The conformance profiles use a sequential model of a representative trace selected by minimum total normalized edit distance among the first 30 completed cases. The training prefix is excluded from scoring. The ADWIN profile can relearn from one completed case after an alarm. The configuration applies to inputs that average more than 35 events per case, which selects this one log in the assessment. [Ostovar results](results/cdrift_ostovar_parallel_to_sequence/pm4py/).
- Kairo uses its public feature, scaling, PCA, clustering, state distribution, and divergence APIs. We run intra-case, resource, and inter-case states with K-means, SOM, or DBSCAN. For the benchmark we convert each divergence signal to alarms using a quantile threshold and take the first eligible window of each consecutive excursion. The previous-window profile uses Jensen–Shannon divergence and the 90th percentile. The recent-window profile uses total variation against the last three windows, twice the signal-window width, and the 95th percentile. We filter sparse and partial windows. The fitted states and thresholds use the full evaluated log, so the estimates are retrospective.
- Window sizing and feature selection use interval length, volume, and observed fields or frequencies. Parameters never use a log's drift labels. Feature matrix and DBSCAN limits keep high-cardinality logs tractable. An unsupported result records the reason, such as a missing resource field or a clustering that labeled every observation as noise.
- Each method on a given log receives the same margin around the annotated point or transition interval. The primary margin is 2.5% of the observed time span, with 1% and 5% for sensitivity. Matching maximizes the number of one-to-one alarm and truth pairs, then minimizes total timestamp distance to the truth intervals. Duplicate alarms count as false positives. Coincident truth annotations with the same start and end contribute one untyped temporal episode and retain their original labels. Precision without any alarms, plus recall and F1 on no-injection controls, are undefined. F1 is zero on a drifted log when there are zero hits.
- Metrics use estimated timestamps. A trace-order algorithm's calendar estimate can differ from a drift specified at arrival, especially for long or reordered executions. The files retain confirmation times and, for matched alarms, their lag from annotated onset. The common timestamp tolerances also differ from the thesis's window-relative scoring and its hand-tuned Run 2 configurations.
- Every alarm is retained. For a dense evidence series, the published scores retain regularly spaced observations, alarm-linked indices, and the last observation. Each result records the stride and full observation count. The runner can also produce full series.

## PM4Py implementation checks

- The original Bose detector could miss an abrupt change after a harmless permutation of case identifiers. The fix orders cases by their first event, honors configured column names, preserves source events in returned segments, and excludes a trailing partial block from the permutation test. In the generated insertion check, the original detector found the January 31 change only with ordered identifiers. The fixed detector found it with both identifier assignments. [Before-and-after JSON](diagnostics/bose-case-id-order.json), [chronology fix](https://gitlab.com/process-intelligence-solutions/pm4py/-/commit/79b6ce1b025e48be760faed10041d0e33acd0b8c).
- The original code counted incoming eventually-follows relations. The paper's Relation Type Count counts outgoing relations. The correction reproduces the paper's worked example. An isolated substitution from `A,B` to `A,C` preserves the outgoing counts, so the corrected variant produces no alarm in that fixture. [Bose et al., sections 4.1 and 4.2](https://www.vdaalst.com/publications/p623.pdf), [feature fix](https://gitlab.com/process-intelligence-solutions/pm4py/-/commit/765435bc7f5190adf30be7314d7158b92ff433c4).
- The outgoing-count change kept three of the four Bose archive matches and reduced false alarms from 17 to 12. The missed change at 2,400 cases is also the one the paper's Relation Type Count misses. On the Ostovar parallel-to-sequence log it raised matches from one to two while keeping seven false alarms. The correction preserves the feature definition, and its effect on measured performance varies by log. [Archived before-and-after JSON](diagnostics/bose-archive-effect.json), [Bose et al., section 5.2](https://www.vdaalst.com/publications/p623.pdf).
- Ostovar Loop contains 2,921 distinct activity sequences in 2,999 cases, and 2,848 occur only once. At the second boundary, the two wide windows share zero exact variants. The observed Jensen–Shannon distance can be maximal while a shuffle also produces almost disjoint variants. Adjacent-window DFG G-tests locate both changes about 26 hours after the case-start annotations. That gives zero matches at 2.5% and two at 5%. [Trace-variant frequency](results/cdrift_ostovar_loop/pm4py/trace-variant-frequency/permutation-wide.json), [wide DFG](results/cdrift_ostovar_loop/pm4py/dfg-frequency/g-test-wide.json).
- Ceravolo's start and completion timestamps are identical for every event. The timing configurations use completion gaps on these logs so their timing features carry information. Service times are used when real start and completion differences are available for the selected profile.
- In an additional Earth Mover test, the untimed Bose log reached F1 0.571 with 100 traces per window and 0.400 with 200 at the same alarm threshold. On the three Ceravolo logs, the wider-window maxima fell between 0.080 and 0.164, below the 0.20 threshold, even though some maxima were close to the known drift. This check used the same transport implementation and changed the width and evaluation step. [Wider-window diagnostics](diagnostics/emd-sensitivity/).

## Reproduce

From the repository root after syncing the thesis environment, check out the final PM4Py commit in the manifest's `pm4py_method_revisions.bose` field. The published Bose runs use this revision. The other published runs record the preceding revision, which has identical source for those variants. A fresh run on the final commit uses the same detector implementations throughout.

```bash
uv sync
uv pip install --python .venv/bin/python 'hdbscan==0.8.44' 'river==0.27.0' 'pyemd==2.0.0'
.venv/bin/python -m scripts.drift_benchmark.run \
  --pm4py /home/javert/PIS/pm4py \
  --data-dir /tmp/kairo-drift-data \
  --output /tmp/kairo-drift-results \
  --jobs 8
.venv/bin/python -m scripts.drift_benchmark.verify \
  --pm4py /home/javert/PIS/pm4py /tmp/kairo-drift-results
```

The input cache keeps the public downloads separate from the repository. Start a complete run with a fresh output directory. Use `--resume` after an interruption when running the same benchmark adapter. Pass repeated `--dataset` options for a subset, `--library` and `--method` to isolate a detector, or `--full-scores` to keep dense evidence intact.

The optional diagnostic runners use the same three path arguments as the main runner. Run `python -m scripts.drift_benchmark.emd_sensitivity` for the wider Earth Mover tests or `python -m scripts.drift_benchmark.case_composition` for the Rheon case-attribute tests.
