\section{Implementation}\label{sec:implementation}

Kairo provides a Python library and a browser-based dashboard that uses the library for its computations. The library is designed for scripted experiments and for extending the analysis. The dashboard presents the same stages in a guided workflow and gives analysts plots and summaries for deciding which settings to try next. The benchmark runs the library with the alarm rule in \Cref{sec:assessment-config}.

\subsection{Analysis Library}
\label{sec:implementation-library}

The library exposes separate operations for preparing a log, building and transforming feature matrices, learning states, and comparing their distributions. Intermediate tables retain timestamps and, where applicable, case identifiers. This lets an analyst link a state back to the observation it describes. The metadata is kept separate from the numerical inputs to scaling, projection, and clustering. Analysts can provide their own numerical features or compatible state assignments and reuse the remaining stages. This makes it possible, for example, to compare the effect of adding a workload measure while keeping the choice of clustering method and drift settings fixed.

\autoref{tab:implementation-inputs} describes the choices before clustering. They determine which changes can be seen and how much information the state model has to summarize. In the resource perspective, selecting a subset of resources limits the output columns while preserving the full set of observed resources in the denominators of the retained shares. In the inter-case perspective, selecting the type of each case attribute determines whether the feature describes numerical values or the mix of categories. Kairo keeps these matrices in memory, so selecting feature groups or resources also helps control matrix width when a log contains many activities or resources.

\autoref{tab:implementation-models} describes the choices from learning states to reading a drift signal. Changing the clustering method or its settings can change which observations share a state. Changing the signal window or reference changes the comparison while reusing the state assignments. For density-based clustering, the library combines identical vectors with weights that preserve their counts, then assigns the resulting labels back to the original observations. This reduces the number of points used to build neighborhoods when prefixes or windows repeat.

import kairo
import pandas as pd

csv_path = input("Enter the path to the CSV log: ")
log = kairo.read_log(
    csv_path, case_id="case", activity="activity",
    timestamp="completed_at",
)
time = "time:timestamp"
log[time] = pd.to_datetime(log[time], utc=True, format="mixed")

features = kairo.compute_features_intra(log)
scaled = kairo.standardize(features, "minmax")
model = kairo.compute_kmeans(scaled, k=3)
meta = ["case:concept:name", time]
states = scaled[meta].join(kairo.get_kmeans_states(scaled, model))

weekly = kairo.compute_state_distributions(states, "7D")
previous = kairo.compute_drift_signal(weekly, divergence="js")
kairo.plot_drift_signal(previous, divergence="js").show()
\end{lstlisting}

\subsection{Graphical Interface}
\label{sec:implementation-dashboard}

The dashboard opens with log upload and column mapping, then offers the same sequence of pages for each perspective. The analyst can inspect examples in the feature table and open a glossary to see how each feature group is computed. Preset feature and signal window lengths provide starting points. Controls appear where they apply, such as a history length for lagged activities or a lookback length for the recent-window reference. Case attribute features appear when the required attribute types are mapped. The dashboard remembers selections as the analyst moves between pages. Rerunning a stage clears its downstream results for that perspective, so a new analysis follows the changed settings.

\autoref{tab:implementation-views} shows how each view supports a decision. The analyst can refine the feature window or projection while looking at the intermediate output, then inspect the resulting states with the diagnostic measures in \cref{def:cluster-diagnostics}. In the drift view, the threshold slider helps locate candidate windows. The analyst can then compare the state distributions and observation counts around the peak, as illustrated in \autoref{fig:implementation-dashboard}. In the resource perspective, for example, an analyst can investigate a suspected reassignment by comparing state frequencies across date ranges and checking the assignment or handover features for the relevant windows.
